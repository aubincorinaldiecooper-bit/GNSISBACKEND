# AGENTS.md — Desktop Host

This subtree implements the GNSIS Desktop Host. In addition to the repository-root brief, computer-use work here is governed by `docs/computer-use/AGENTS.md` — treat that document as binding for any task under `desktop/**`. Its non-negotiable rules restated for this tree:

## Binding rules for `desktop/**`

- **One persistent visual sense.** All perception stills derive from the live screen/camera stream; never reintroduce a screenshot-based perception path. Generic desktop UI observation uses the already-active capture lifecycle.
- **No second execution stack.** Local actions plug into `ToolRegistry` and the existing Host/daemon seams — do not build a parallel action framework beside them.
- **Bidirectional tool routing is required, not optional.** When the runtime emits an external tool call and awaits a client `tool.response`, the Host must execute the call through `ToolRegistry` and return a correlated response. A tool that is registered but unreachable from the model is not done.
- **Bind actions to authenticated user intent.** Model-generated tool calls can be induced by untrusted text on screen or in a document. Every external tool call must carry normalized provenance bound to a trusted turn. Ordinary non-destructive read/navigation actions directly and unambiguously requested by the user may execute within scope without redundant confirmation; untrusted-content-induced, out-of-scope, destructive, credential-adjacent, publishing/submission, payment, security/account-state, or otherwise consequential actions follow the governing brief's confirmation/refusal policy.
- **Permissions are explicit state, never implicit grants.** Microphone, camera, screen and Accessibility are explicit state. If the selected native mechanism uses Apple Events, Automation consent is tracked against the concrete target application rather than modeled as one global Boolean. Missing consent fails with attributable permission-denied telemetry — never a silent no-op or implicit grant.
- **Sequencing.** Follow the brief's Phase 0 → PR H → PR 0 → PR A → PR B → PR C → PR D → PR E order. PR H fixes the five verified realtime Host correctness bugs before any computer-use latency/reliability baseline; PR 0 closes model↔Host local-tool routing before adapters.
- **Measurement/testing.** In addition to adapter/lifecycle tests, inherit the governing brief's correlation IDs, provenance/policy fields, capability-manifest identity, per-stage timestamps, duplicate/replay counters, macOS TCC evidence, and Host realtime correctness measurements. Linux/CI mocks never count as real-Mac acceptance.

- **Host correctness gate is binding.** Before computer-use baselines, fix and measure: socket errors must not crash Electron main; streamed playback chunks must not overlap; daemon playback cancellation must stop/discard stale local audio and emit authoritative cancellation; worklet resampling must preserve fractional phase across callbacks and sustain the intended 16 kHz ratio; mic mute/unmute must not leave the UI sending into a dead session.
- **Preserve shipped fixes.** Do not reopen or regress #106 preload-as-`preload.mjs` or #111 token-gated screen socket opening without concrete regression evidence.

## Interface rules — set by the owner, 29 and 30 September 2026

These are the owner's instructions. They bind every change to the GNSIS desktop app: the interface under `desktop/ui/**`, the Electron renderer, and the main process where a rule names it.

- **The current interface stays** (30 September). The owner saw the interface rebuilt on the Beautiful UI kit (https://github.com/slev12397/beautiful-ui), found it too generic, and kept the existing interface with adjustments. The 29 September rules "Beautiful UI only" and "when the kit has nothing, stop and ask" are withdrawn. A kit component is used only where the owner points to it.
- **Ask before adding any detail** (30 September). No element, label, tag, icon, caption, status line, card or wording goes into the interface unless the owner asked for it. If a change seems to need one, describe it and ask first. Removing what the owner asked to remove is never a reason to put something else in its place.
- **Dark mode: on hold.** On 29 September the owner asked for dark mode only, for the kit version. The interface kept on 30 September is light. Ask the owner before changing its colours either way.
- **Show before building.** Every change is shown to the owner first — pictures or a video made from a separate mockup for anything visible, a plain-words account of what changes and what the person would notice for anything else — and nothing is written into the app, committed or pushed until the owner says yes.
- **No screenshots.** GNSIS never takes screenshots: not with the Mac's screenshot function (`screencapture`), not with `webContents.capturePage`, not through `desktopCapturer` thumbnails (every `getSources` call passes `thumbnailSize: { width: 0, height: 0 }`), and no screenshot action is ever offered to the model. The only picture of the screen GNSIS has is the live screen share the person turns on, and the small still frames taken from that share while it is on; nothing is saved to disk. `src/main/noScreenshots.test.ts` fails the build if screenshot code appears.
- **Hidden from capture, and wherever the person is** (30 September). Every GNSIS window is left out of screenshots, screen recordings and screen sharing (`setContentProtection`), which also keeps GNSIS's own cards out of the screen picture GNSIS is sent. The floating window appears on every desktop and over full-screen apps (`setVisibleOnAllWorkspaces` with `visibleOnFullScreen`). Both are in `src/main/windowRules.ts`.
- **The chat reads like an ordinary AI chat** (30 September). No chat window above the bar until there is a conversation. The person's turns are their words only: no "Listening…" or "Spoken" tags, no voice bars, no durations, and a spoken turn without words shows nothing. What GNSIS did sits left-aligned in the conversation, with no voice icon. The bar's text field shows no live status; the voice button shows what is happening, with bars in the usual voice-activity shape that never fill the button as one block.
- **GNSIS at work, the way AI chats show it** (30 September; approved from a live mockup: "this works please push"). After the person stops talking, or once a typed message has reached GNSIS, the chat shows "Thinking" with a moving shine and the seconds so far ("3s · Thinking"; from five seconds, "Thinking some more") until GNSIS says something, speaks or takes a step — never while its voice is playing, and in live voice for at most 10 seconds. Each step GNSIS takes on the computer shows as it happens: the running one with a small spinner and the same shine, then a tick when done (without the word "Done:"), an orange hand while it waits for the person's OK, a lock when a permission is missing, a red cross when it failed or was refused. Once GNSIS answers, its steps fold into one line, "Worked for Ns" (from the first step starting to the last one ending), which opens them again; a step that failed, was refused or needs a permission keeps them open. A step always sits below the words GNSIS said before it. Colours are the interface's own.
- **GNSIS can be moved** (30 September; approved from a live demo: "lets push the changes we just did first"). Pressing on an empty part of the bar or dock, on a face, on the chat's top strip or on the drawer's header and dragging moves the bar, the chat and the drawer together. They always stay fully on screen, also when the chat opens or grows near an edge, and the place is remembered for the next launch. Buttons and the text field never start a drag, and letting go after a drag is not a click.
- **The greeting shows once** (30 September). "Hi, I'm your GNSIS" appears on the first launch on a computer only, with a × to close it.
- **Removed on 30 September**: the eye in the bar; and from GNSIS's Activity panel, the "GNSIS · Your assistant" heading, the "GNSIS right now" card, the "Your agents" list and the caption "GNSIS gets smaller still pictures of it".
